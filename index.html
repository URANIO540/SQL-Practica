Caso 1 · Modelo físico

DDL — Data Definition Language

DDL define y administra la estructura de la base de datos: crea, modifica y elimina objetos (bases de datos, tablas, restricciones). No trabaja con los datos, sino con la arquitectura que los sostiene. Con DDL el diseño lógico (entidades, atributos, relaciones) se convierte en una estructura física ejecutable.

CREATE: el punto de partida

Crea objetos nuevos. En el examen normalmente: primero la base de datos, luego USE para trabajar dentro de ella, y después las tablas.

CREATE DATABASE UniversityDB
GO
USE UniversityDB
GO

CREATE TABLE Student (
    StudentID  INT          PRIMARY KEY,
    FirstName  VARCHAR(100) NOT NULL,
    LastName   VARCHAR(100) NOT NULL,
    BirthDate  DATE,
    Email      VARCHAR(150) UNIQUE
)
¿Qué es GO?GO no es SQL: es un separador de lotes de SQL Server Management Studio. Úsalo después de CREATE DATABASE y antes de USE para que la base exista antes de entrar en ella.

Clave autoincremental: IDENTITY

Si el caso dice que el código se genera automáticamente, usa IDENTITY(inicio, incremento). En ese caso no envías ese valor en el INSERT.

CREATE TABLE Employee (
    EmployeeID INT IDENTITY(1,1) PRIMARY KEY,
    FirstName  VARCHAR(100) NOT NULL,
    Salary     DECIMAL(10,2) NOT NULL
)

-- No se envía EmployeeID: lo genera el motor
INSERT INTO Employee (FirstName, Salary) VALUES ('Luis Gomez', 2800.00)

Orden de creaciónCrea primero las tablas independientes (las que no tienen FK) y después las que dependen de ellas. Si creas Enrollment antes que Student, la FK falla porque la tabla referenciada aún no existe.

ALTER: modificar sin eliminar

Permite adaptar el esquema a nuevos requerimientos sin perder la tabla ni sus datos.

-- Agregar una columna
ALTER TABLE Student
ADD Phone VARCHAR(20)

-- Cambiar el tipo de dato (sintaxis de SQL Server)
ALTER TABLE Student
ALTER COLUMN Phone VARCHAR(30)

-- Eliminar una columna
ALTER TABLE Student
DROP COLUMN Phone

-- Agregar una restricción a una tabla existente
ALTER TABLE Student
ADD CONSTRAINT CK_Student_BirthDate CHECK (BirthDate < '2015-01-01')

-- Agregar una FK después de crear las tablas
ALTER TABLE Enrollment
ADD CONSTRAINT FK_Enrollment_Course FOREIGN KEY (CourseID) REFERENCES Course(CourseID)

-- Eliminar una restricción (por eso conviene nombrarlas)
ALTER TABLE Student
DROP CONSTRAINT CK_Student_BirthDate
Ojo con otros motoresEn MySQL se usa MODIFY COLUMN y en PostgreSQL ALTER COLUMN ... TYPE. En el curso se usa SQL Server: ALTER COLUMN.

DROP, TRUNCATE y RENAME

DROP

Elimina el objeto completo: estructura y datos. Úsalo con precaución.

DROP TABLE Student

TRUNCATE

Borra todas las filas, pero la tabla (su definición) sigue existiendo.

TRUNCATE TABLE Student

sp_rename

En SQL Server se renombra con un procedimiento almacenado. Cambia el nombre, no la definición.

EXEC sp_rename 'Student', 'Learner'

DDL y el diccionario de datos

Cada sentencia DDL actualiza el diccionario de datos: los metadatos que describen tablas, columnas, tipos, restricciones, índices y relaciones. El motor los usa para validar todas las operaciones posteriores. En SQL Server se consultan con vistas del sistema:

SELECT * FROM sys.tables          -- tablas existentes
SELECT * FROM sys.columns         -- columnas
SELECT * FROM sys.foreign_keys    -- claves foráneas
EXEC sp_help 'Student'            -- resumen completo de una tabla

-- Alternativa estándar
SELECT TABLE_NAME, COLUMN_NAME, DATA_TYPE, IS_NULLABLE
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 'Student'
DDL en entornos modernosEn ingeniería de datos, el DDL se trata como infraestructura como código: los scripts se versionan y herramientas como dbt generan CREATE/ALTER automáticamente, lo que permite automatizar despliegues y mantener consistencia entre ambientes.
Caso 2 · Manipulación de datos

DML — Data Manipulation Language

Mientras DDL define la estructura, DML trabaja con los datos almacenados en las tablas: insertar, modificar, eliminar y consultar registros. SELECT a veces se clasifica como DQL, pero funcionalmente forma parte de la manipulación de datos.

INSERT: agregar filas

Cada INSERT crea una fila nueva que debe cumplir todas las restricciones de la tabla.

-- Una fila (siempre lista las columnas: es más seguro)
INSERT INTO Employee (EmployeeID, FirstName, Salary)
VALUES (1, 'Luis Gomez', 2800.00)

-- Varias filas en una sola sentencia
INSERT INTO Employee (EmployeeID, FirstName, Salary)
VALUES
(2, 'Ana Torres', 3200.00),
(3, 'Carlos Ruiz', 2500.00)

-- Insertar a partir de una consulta
INSERT INTO EmployeeBackup (EmployeeID, FirstName, Salary)
SELECT EmployeeID, FirstName, Salary FROM Employee WHERE Salary > 3000
Al insertar, verifica • Columnas NOT NULL con valor.
• La PK no se repite.
• El valor de cada FK ya existe en la tabla padre → inserta primero en las tablas padre y luego en las hijas.
• Los CHECK se cumplen (ej. nota entre 0 y 20).
• Textos y fechas van entre comillas simples: '2026-10-11'. Números sin comillas.
• Si la PK es IDENTITY, no la envíes.

UPDATE: modificar filas existentes

Operación crítica: sin un WHERE correcto afecta a todas las filas.

-- Aumentar 10% el salario solo del área de ventas
UPDATE Employee
SET Salary = Salary * 1.10
WHERE Department = 'Sales'

-- Varias columnas a la vez
UPDATE Employee
SET Department = 'IT', Salary = 3500.00
WHERE EmployeeID = 2

-- Asignar NULL
UPDATE Student SET Email = NULL WHERE StudentID = 5

-- Valor condicional con CASE
UPDATE Matriculas
SET estado = CASE WHEN nota >= 13 THEN 'Aprobada' ELSE 'Desaprobada' END
WHERE nota IS NOT NULL
Sin WHEREUPDATE Employee SET Salary = Salary * 1.10 modifica todos los registros de la tabla. Truco: escribe primero el SELECT * FROM ... WHERE ..., comprueba qué filas devuelve y recién cambia a UPDATE.

DELETE: eliminar filas

DELETE FROM Employee
WHERE EmployeeID = 1

-- Sin WHERE: borra todas las filas, la tabla sigue existiendo
DELETE FROM Employee

Las claves foráneas pueden impedir la eliminación si existen filas hijas que dependen de la fila que intentas borrar. Opciones:

-- Opción 1: borrar primero las hijas y luego el padre
DELETE FROM Enrollment WHERE StudentID = 10
DELETE FROM Student    WHERE StudentID = 10

-- Opción 2: definir la FK con borrado en cascada (en el DDL)
CONSTRAINT FK_Enrollment_Student FOREIGN KEY (StudentID)
    REFERENCES Student(StudentID) ON DELETE CASCADE
Error típico en SQL Server"The DELETE statement conflicted with the REFERENCE constraint FK_..." significa que hay filas hijas. Por eso conviene nombrar las FK: el mensaje te dice exactamente cuál es.

DML y control transaccional

Los cambios hechos con DML no son permanentes hasta ejecutar COMMIT. Antes de eso, solo el usuario que hace los cambios los ve, se pueden revertir con ROLLBACK, y los demás usuarios siguen viendo el estado consistente anterior. Esto garantiza atomicidad (todo o nada) y consistencia.

BEGIN TRANSACTION

    UPDATE Cuentas SET saldo = saldo - 500 WHERE id_cuenta = 1
    UPDATE Cuentas SET saldo = saldo + 500 WHERE id_cuenta = 2

    -- Si todo salió bien:
COMMIT
    -- Si algo falló: ROLLBACK  (deshace ambos UPDATE)

-- Versión con control de errores
BEGIN TRY
    BEGIN TRANSACTION
        DELETE FROM Matriculas  WHERE id_estudiante = 10
        DELETE FROM Estudiantes WHERE id_estudiante = 10
    COMMIT
END TRY
BEGIN CATCH
    ROLLBACK
    PRINT ERROR_MESSAGE()
END CATCH
Dato de SQL ServerPor defecto SQL Server trabaja en modo autocommit: cada sentencia suelta se confirma sola. Solo dentro de BEGIN TRANSACTION puedes hacer ROLLBACK.
Consultas

La sentencia SELECT

Recupera información de una o más tablas. Permite filtrar filas, proyectar columnas, agrupar, aplicar funciones de agregación y ordenar.

Orden de escritura

SELECT→FROM→WHERE→GROUP BY→HAVING→ORDER BY

Columnas a mostrar · tablas origen · filtra filas · agrupa · filtra grupos · ordena.

Orden lógico de procesamiento

FROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BY

El motor procesa en este orden. Por eso un alias del SELECT no se puede usar en WHERE, pero sí en ORDER BY.

SELECT name, COUNT(OrderID) AS TotalPedidos
FROM Orders
WHERE status = 'Completed'          -- filtra FILAS (antes de agrupar)
GROUP BY name
HAVING COUNT(OrderID) > 5           -- filtra GRUPOS (después de agrupar)
ORDER BY TotalPedidos DESC          -- aquí ya se puede usar el alias

Caso: Universidad

Enunciado

Una universidad necesita registrar sus carreras (código, nombre que no se repite y facultad). De cada estudiante se guarda código, nombres, apellidos, correo electrónico (no se repite), fecha de nacimiento y ciudad (si no se indica, es Lima). Cada estudiante pertenece a una sola carrera.

Los cursos tienen código, nombre, créditos (de 1 a 6) y costo (no negativo). Un estudiante se matricula en varios cursos y un curso tiene muchos estudiantes; de cada matrícula se registra el ciclo, la nota (de 0 a 20, queda vacía hasta que termine el ciclo) y el estado (Activa, Retirada, Aprobada o Desaprobada; por defecto Activa).

Durante el ciclo ocurren diversas situaciones:

  • Nuevos estudiantes se registran y se matriculan en cursos.
  • Al terminar el ciclo se registran las notas y se actualiza el estado de las matrículas.
  • La universidad ajusta el costo de algunos cursos.
  • Se eliminan las matrículas retiradas y, en ocasiones, un estudiante deja la universidad.

Enunciado

La empresa LearnHub ofrece una plataforma de aprendizaje en línea donde los estudiantes pueden registrarse y matricularse en distintos cursos disponibles. En el sistema se almacena información sobre estudiantes, cursos y matrículas.

El estilo de la profesora En sus casos usa nombres en plural (Estudiantes, Matriculas), columnas en minúscula con guion bajo (id_estudiante, fecha_matricula) y FK sin nombre (FOREIGN KEY (...) REFERENCES ...). Las dos formas son correctas, pero en el examen conviene usar su estilo para que tus sentencias calcen con sus nombres de tabla y columna.
Pista escondida en la pregunta 1 El INSERT solo envía (nombre, correo). Eso significa que id_estudiante se genera solo (IDENTITY) y que fecha_registro tiene DEFAULT GETDATE(). Si la tabla no estuviera diseñada así, ese INSERT fallaría.

Cómo razonar cada espacio en blanco Textos y fechas → entre comillas simples. Números (los id) → sin comillas. En el UPDATE, el SET lleva la columna que cambia y el WHERE la columna que identifica la fila (la PK). En el DELETE, borras de la tabla donde está el registro equivocado (Matriculas, no Estudiantes).

Checklist del examen

Caso 1 · Modelo físico

  • CREATE DATABASE + GO + USE al inicio.
  • Una tabla por entidad; las N:M tienen tabla intermedia.
  • Todas las tablas tienen PRIMARY KEY.
  • FK en el lado "muchos", con el mismo tipo de dato que la PK referenciada.
  • Tipos correctos: dinero en DECIMAL, DNI/teléfono en CHAR/VARCHAR, fechas en DATE.
  • UNIQUE, CHECK, DEFAULT y NOT NULL que pide el enunciado.
  • Nombres al estilo de la profesora: tablas en plural, columnas tipo id_cliente.
  • Tablas padre creadas antes que las hijas.
  • Comas entre columnas y ninguna coma antes del paréntesis final.

Caso 2 · DML

  • INSERT con lista de columnas explícita.
  • Insertar primero en tablas padre, luego en hijas.
  • No enviar columnas IDENTITY.
  • Textos y fechas entre comillas simples; números sin comillas.
  • Todo UPDATE y DELETE con WHERE (salvo que pidan afectar todo).
  • Para borrar un padre, borrar antes sus filas hijas.
  • IS NULL, nunca = NULL.
  • Columnas no agregadas del SELECT presentes en el GROUP BY.
  • WHERE filtra filas; HAVING filtra grupos.
