Caso 1 · Modelo físico

DDL — Data Definition Language

DDL define y administra la estructura de la base de datos: crea, modifica y elimina objetos (bases de datos, tablas, restricciones). No trabaja con los datos, sino con la arquitectura que los sostiene. Con DDL el diseño lógico (entidades, atributos, relaciones) se convierte en una estructura física ejecutable.

CREATE: el punto de partida

Crea objetos nuevos. En el examen normalmente: primero la base de datos, luego USE para trabajar dentro de ella, y después las tablas.

CREATE DATABASE UniversityDB
GO
USE UniversityDB
GO

CREATE TABLE Student (
    StudentID  INT          PRIMARY KEY,
    FirstName  VARCHAR(100) NOT NULL,
    LastName   VARCHAR(100) NOT NULL,
    BirthDate  DATE,
    Email      VARCHAR(150) UNIQUE
)
¿Qué es GO?GO no es SQL: es un separador de lotes de SQL Server Management Studio. Úsalo después de CREATE DATABASE y antes de USE para que la base exista antes de entrar en ella.

Clave autoincremental: IDENTITY

Si el caso dice que el código se genera automáticamente, usa IDENTITY(inicio, incremento). En ese caso no envías ese valor en el INSERT.

CREATE TABLE Employee (
    EmployeeID INT IDENTITY(1,1) PRIMARY KEY,
    FirstName  VARCHAR(100) NOT NULL,
    Salary     DECIMAL(10,2) NOT NULL
)

-- No se envía EmployeeID: lo genera el motor
INSERT INTO Employee (FirstName, Salary) VALUES ('Luis Gomez', 2800.00)

Regla práctica para el examenDNI, teléfono y RUC son texto (CHAR/VARCHAR), no números: no se suman y pueden empezar con 0. El dinero siempre en DECIMAL(10,2) o MONEY, nunca en INT ni FLOAT.

Restricciones de integridad

Uno de los roles más importantes del DDL es fijar reglas que mantienen la consistencia de los datos. El motor rechaza cualquier INSERT/UPDATE/DELETE que las viole.

Restricciones nombradas (buena práctica del curso)

Nombrar las restricciones con CONSTRAINT facilita leer errores y modificarlas luego. Convención: PK_Tabla, FK_Hija_Padre, UQ_Tabla_Columna, CK_Tabla_Columna, DF_Tabla_Columna.

CREATE TABLE Enrollment (
    EnrollmentID   INT  NOT NULL,
    StudentID      INT  NOT NULL,
    EnrollmentDate DATE NOT NULL CONSTRAINT DF_Enrollment_Date DEFAULT GETDATE(),
    Grade          DECIMAL(4,1) NULL,
    CONSTRAINT PK_Enrollment PRIMARY KEY (EnrollmentID),
    CONSTRAINT FK_Enrollment_Student FOREIGN KEY (StudentID)
        REFERENCES Student(StudentID),
    CONSTRAINT CK_Enrollment_Grade CHECK (Grade BETWEEN 0 AND 20)
)

Clave primaria compuesta

Cuando una fila se identifica por la combinación de dos columnas (típico en tablas intermedias N:M):

CREATE TABLE DetallePedido (
    PedidoID   INT NOT NULL,
    ProductoID INT NOT NULL,
    Cantidad   INT NOT NULL CHECK (Cantidad > 0),
    CONSTRAINT PK_DetallePedido PRIMARY KEY (PedidoID, ProductoID),
    CONSTRAINT FK_Detalle_Pedido   FOREIGN KEY (PedidoID)   REFERENCES Pedido(PedidoID),
    CONSTRAINT FK_Detalle_Producto FOREIGN KEY (ProductoID) REFERENCES Producto(ProductoID)
)
Orden de creaciónCrea primero las tablas independientes (las que no tienen FK) y después las que dependen de ellas. Si creas Enrollment antes que Student, la FK falla porque la tabla referenciada aún no existe.

ALTER: modificar sin eliminar

Permite adaptar el esquema a nuevos requerimientos sin perder la tabla ni sus datos.

-- Agregar una columna
ALTER TABLE Student
ADD Phone VARCHAR(20)

-- Cambiar el tipo de dato (sintaxis de SQL Server)
ALTER TABLE Student
ALTER COLUMN Phone VARCHAR(30)

-- Eliminar una columna
ALTER TABLE Student
DROP COLUMN Phone

-- Agregar una restricción a una tabla existente
ALTER TABLE Student
ADD CONSTRAINT CK_Student_BirthDate CHECK (BirthDate < '2015-01-01')

-- Agregar una FK después de crear las tablas
ALTER TABLE Enrollment
ADD CONSTRAINT FK_Enrollment_Course FOREIGN KEY (CourseID) REFERENCES Course(CourseID)

-- Eliminar una restricción (por eso conviene nombrarlas)
ALTER TABLE Student
DROP CONSTRAINT CK_Student_BirthDate
Ojo con otros motoresEn MySQL se usa MODIFY COLUMN y en PostgreSQL ALTER COLUMN ... TYPE. En el curso se usa SQL Server: ALTER COLUMN.

DROP, TRUNCATE y RENAME

DROP

Elimina el objeto completo: estructura y datos. Úsalo con precaución.

DROP TABLE Student

TRUNCATE

Borra todas las filas, pero la tabla (su definición) sigue existiendo.

TRUNCATE TABLE Student

sp_rename

En SQL Server se renombra con un procedimiento almacenado. Cambia el nombre, no la definición.

EXEC sp_rename 'Student', 'Learner'
-- columna:
EXEC sp_rename 'Student.Phone', 'Celular', 'COLUMN'

DDL y el diccionario de datos

Cada sentencia DDL actualiza el diccionario de datos: los metadatos que describen tablas, columnas, tipos, restricciones, índices y relaciones. El motor los usa para validar todas las operaciones posteriores. En SQL Server se consultan con vistas del sistema:

SELECT * FROM sys.tables          -- tablas existentes
SELECT * FROM sys.columns         -- columnas
SELECT * FROM sys.foreign_keys    -- claves foráneas
EXEC sp_help 'Student'            -- resumen completo de una tabla

-- Alternativa estándar
SELECT TABLE_NAME, COLUMN_NAME, DATA_TYPE, IS_NULLABLE
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 'Student'
DDL en entornos modernosEn ingeniería de datos, el DDL se trata como infraestructura como código: los scripts se versionan y herramientas como dbt generan CREATE/ALTER automáticamente, lo que permite automatizar despliegues y mantener consistencia entre ambientes.
Caso 2 · Manipulación de datos

DML — Data Manipulation Language

Mientras DDL define la estructura, DML trabaja con los datos almacenados en las tablas: insertar, modificar, eliminar y consultar registros. SELECT a veces se clasifica como DQL, pero funcionalmente forma parte de la manipulación de datos.

INSERT: agregar filas

Cada INSERT crea una fila nueva que debe cumplir todas las restricciones de la tabla.

-- Una fila (siempre lista las columnas: es más seguro)
INSERT INTO Employee (EmployeeID, FirstName, Salary)
VALUES (1, 'Luis Gomez', 2800.00)

-- Varias filas en una sola sentencia
INSERT INTO Employee (EmployeeID, FirstName, Salary)
VALUES
(2, 'Ana Torres', 3200.00),
(3, 'Carlos Ruiz', 2500.00)

-- Insertar a partir de una consulta
INSERT INTO EmployeeBackup (EmployeeID, FirstName, Salary)
SELECT EmployeeID, FirstName, Salary FROM Employee WHERE Salary > 3000
Al insertar, verifica • Columnas NOT NULL con valor.
• La PK no se repite.
• El valor de cada FK ya existe en la tabla padre → inserta primero en las tablas padre y luego en las hijas.
• Los CHECK se cumplen (ej. nota entre 0 y 20).
• Textos y fechas van entre comillas simples: '2026-10-11'. Números sin comillas.
• Si la PK es IDENTITY, no la envíes.

UPDATE: modificar filas existentes

Operación crítica: sin un WHERE correcto afecta a todas las filas.

-- Aumentar 10% el salario solo del área de ventas
UPDATE Employee
SET Salary = Salary * 1.10
WHERE Department = 'Sales'

-- Varias columnas a la vez
UPDATE Employee
SET Department = 'IT', Salary = 3500.00
WHERE EmployeeID = 2

-- Asignar NULL
UPDATE Student SET Email = NULL WHERE StudentID = 5

-- Valor condicional con CASE
UPDATE Matricula
SET Estado = CASE WHEN Nota >= 13 THEN 'Aprobada' ELSE 'Desaprobada' END
WHERE Nota IS NOT NULL
Sin WHEREUPDATE Employee SET Salary = Salary * 1.10 modifica todos los registros de la tabla. Truco: escribe primero el SELECT * FROM ... WHERE ..., comprueba qué filas devuelve y recién cambia a UPDATE.

DELETE: eliminar filas

DELETE FROM Employee
WHERE EmployeeID = 1

-- Sin WHERE: borra todas las filas, la tabla sigue existiendo
DELETE FROM Employee

Las claves foráneas pueden impedir la eliminación si existen filas hijas que dependen de la fila que intentas borrar. Opciones:

-- Opción 1: borrar primero las hijas y luego el padre
DELETE FROM Enrollment WHERE StudentID = 10
DELETE FROM Student    WHERE StudentID = 10

-- Opción 2: definir la FK con borrado en cascada (en el DDL)
CONSTRAINT FK_Enrollment_Student FOREIGN KEY (StudentID)
    REFERENCES Student(StudentID) ON DELETE CASCADE
Error típico en SQL Server"The DELETE statement conflicted with the REFERENCE constraint FK_..." significa que hay filas hijas. Por eso conviene nombrar las FK: el mensaje te dice exactamente cuál es.

DML y control transaccional

Los cambios hechos con DML no son permanentes hasta ejecutar COMMIT. Antes de eso, solo el usuario que hace los cambios los ve, se pueden revertir con ROLLBACK, y los demás usuarios siguen viendo el estado consistente anterior. Esto garantiza atomicidad (todo o nada) y consistencia.

BEGIN TRANSACTION

    UPDATE Cuenta SET Saldo = Saldo - 500 WHERE CuentaID = 1
    UPDATE Cuenta SET Saldo = Saldo + 500 WHERE CuentaID = 2

    -- Si todo salió bien:
COMMIT
    -- Si algo falló: ROLLBACK  (deshace ambos UPDATE)

-- Versión con control de errores
BEGIN TRY
    BEGIN TRANSACTION
        DELETE FROM Matricula  WHERE EstudianteID = 10
        DELETE FROM Estudiante WHERE EstudianteID = 10
    COMMIT
END TRY
BEGIN CATCH
    ROLLBACK
    PRINT ERROR_MESSAGE()
END CATCH
Dato de SQL ServerPor defecto SQL Server trabaja en modo autocommit: cada sentencia suelta se confirma sola. Solo dentro de BEGIN TRANSACTION puedes hacer ROLLBACK.
Consultas

La sentencia SELECT

Recupera información de una o más tablas. Permite filtrar filas, proyectar columnas, agrupar, aplicar funciones de agregación y ordenar.

Orden de escritura

SELECT→FROM→WHERE→GROUP BY→HAVING→ORDER BY

Columnas a mostrar · tablas origen · filtra filas · agrupa · filtra grupos · ordena.

Orden lógico de procesamiento

FROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BY

El motor procesa en este orden. Por eso un alias del SELECT no se puede usar en WHERE, pero sí en ORDER BY.

SELECT name, COUNT(OrderID) AS TotalPedidos
FROM Orders
WHERE status = 'Completed'          -- filtra FILAS (antes de agrupar)
GROUP BY name
HAVING COUNT(OrderID) > 5           -- filtra GRUPOS (después de agrupar)
ORDER BY TotalPedidos DESC          -- aquí ya se puede usar el alias

Funciones de agregación

SELECT COUNT(*)        AS Filas,          -- cuenta filas
       COUNT(Email)    AS ConEmail,       -- cuenta valores NO nulos
       SUM(Salary)     AS Planilla,
       AVG(Salary)     AS Promedio,

       MAX(Salary)     AS Maximo
FROM Employee
Regla de oro del GROUP BYToda columna del SELECT que no esté dentro de una función de agregación debe aparecer en el GROUP BY.

Más herramientas útiles

SELECT DISTINCT Ciudad FROM Estudiante                 -- sin repetidos
SELECT TOP 3 * FROM Curso ORDER BY Costo DESC          -- los 3 más caros (SQL Server)
SELECT Nombres + ' ' + Apellidos AS NombreCompleto FROM Estudiante   -- concatenar
SELECT * FROM Estudiante WHERE YEAR(FechaNac) = 2004   -- parte de una fecha

-- Unir tablas (JOIN) usando la FK
SELECT e.Nombres, c.Nombre AS Curso, m.Nota
FROM Matricula m
INNER JOIN Estudiante e ON e.EstudianteID = m.EstudianteID
INNER JOIN Curso c      ON c.CursoID      = m.CursoID
WHERE m.Ciclo = '2026-1'

-- LEFT JOIN: incluye también las filas sin coincidencia
SELECT ca.Nombre, COUNT(e.EstudianteID) AS Alumnos
FROM Carrera ca
LEFT JOIN Estudiante e ON e.CarreraID = ca.CarreraID
GROUP BY ca.Nombre
Técnica para el caso 1

Del enunciado al modelo físico

El caso será un texto. Tu trabajo es leerlo como un diseñador: cada frase te da una tabla, una columna, una clave o una restricción.

Si el enunciado dice…En el modelo físico es…
"Se registra a cada cliente / producto / empleado…"Una tabla (sustantivo importante = entidad)
"De cada cliente se guarda su nombre, DNI y teléfono"Columnas con su tipo de dato
"Cada cliente se identifica con un código"PRIMARY KEY (con IDENTITY si es automático)
"El DNI / correo no puede repetirse"UNIQUE
"Es obligatorio registrar…"NOT NULL
"El precio debe ser mayor a cero", "la nota va de 0 a 20", "el estado puede ser A, B o C"CHECK (Precio > 0), CHECK (Nota BETWEEN 0 AND 20), CHECK (Estado IN ('A','B','C'))
"Si no se indica, el estado es 'Pendiente'", "la fecha es la del registro"DEFAULT 'Pendiente', DEFAULT GETDATE()
"Un pedido pertenece a un cliente; un cliente tiene muchos pedidos" (1:N)FK en el lado N: Pedido.ClienteID → Cliente
"Un pedido tiene muchos productos y un producto está en muchos pedidos" (N:M)Tabla intermedia DetallePedido con dos FK (y sus propios atributos: cantidad, precio)
"Un empleado tiene un único carnet" (1:1)FK con UNIQUE en una de las tablas
Procedimiento en 6 pasos 1) Subraya sustantivos → tablas. 2) Lista atributos de cada una. 3) Elige la PK. 4) Detecta relaciones y cardinalidad → FK o tabla intermedia. 5) Agrega restricciones del texto (UNIQUE, CHECK, DEFAULT, NOT NULL). 6) Ordena: primero tablas padre, luego hijas.
Caso tipo examen

Caso resuelto: Universidad

Enunciado

Una universidad necesita registrar sus carreras (código, nombre único y facultad). De cada estudiante se guarda código, nombres, apellidos, correo (no se repite y es opcional), fecha de nacimiento y ciudad (si no se indica, es Lima). Cada estudiante pertenece a una sola carrera. Los cursos tienen código, nombre, créditos (de 1 a 6) y costo (no negativo). Un estudiante se matricula en varios cursos y un curso tiene muchos estudiantes; de cada matrícula se registra el ciclo, la nota (0 a 20, puede quedar vacía) y el estado (Activa, Retirada, Aprobada o Desaprobada; por defecto Activa). Un estudiante no puede matricularse dos veces en el mismo curso en el mismo ciclo.

CREATE DATABASE UniversidadDB
GO
USE UniversidadDB
GO

-- 1) Tablas independientes primero
CREATE TABLE Carrera (
    CarreraID INT          NOT NULL,
    Nombre    VARCHAR(100) NOT NULL,
    Facultad  VARCHAR(80)  NOT NULL,
    CONSTRAINT PK_Carrera PRIMARY KEY (CarreraID),
    CONSTRAINT UQ_Carrera_Nombre UNIQUE (Nombre)
)
GO

CREATE TABLE Curso (
    CursoID  INT           NOT NULL,
    Nombre   VARCHAR(100)  NOT NULL,
    Creditos INT           NOT NULL,
    Costo    DECIMAL(8,2)  NOT NULL,
    CONSTRAINT PK_Curso PRIMARY KEY (CursoID),
    CONSTRAINT CK_Curso_Creditos CHECK (Creditos BETWEEN 1 AND 6),
    CONSTRAINT CK_Curso_Costo    CHECK (Costo >= 0)
)
GO

-- 2) Tablas que dependen de otras
CREATE TABLE Estudiante (
    EstudianteID INT          NOT NULL,
    Nombres      VARCHAR(100) NOT NULL,
    Apellidos    VARCHAR(100) NOT NULL,
    Email        VARCHAR(150) NULL,
    FechaNac     DATE         NULL,
    Ciudad       VARCHAR(60)  NOT NULL CONSTRAINT DF_Estudiante_Ciudad DEFAULT 'Lima',
    CarreraID    INT          NOT NULL,
    CONSTRAINT PK_Estudiante PRIMARY KEY (EstudianteID),
    CONSTRAINT UQ_Estudiante_Email UNIQUE (Email),
    CONSTRAINT FK_Estudiante_Carrera FOREIGN KEY (CarreraID)
        REFERENCES Carrera(CarreraID)
)
GO

-- 3) Tabla intermedia (resuelve N:M)
CREATE TABLE Matricula (
    MatriculaID  INT          NOT NULL,
    EstudianteID INT          NOT NULL,
    CursoID      INT          NOT NULL,
    Ciclo        VARCHAR(7)   NOT NULL,
    Nota         DECIMAL(4,1) NULL,
    Estado       VARCHAR(12)  NOT NULL CONSTRAINT DF_Matricula_Estado DEFAULT 'Activa',
    CONSTRAINT PK_Matricula PRIMARY KEY (MatriculaID),
    CONSTRAINT FK_Matricula_Estudiante FOREIGN KEY (EstudianteID)
        REFERENCES Estudiante(EstudianteID),
    CONSTRAINT FK_Matricula_Curso FOREIGN KEY (CursoID)
        REFERENCES Curso(CursoID),
    CONSTRAINT CK_Matricula_Nota   CHECK (Nota BETWEEN 0 AND 20),
    CONSTRAINT CK_Matricula_Estado CHECK (Estado IN ('Activa','Retirada','Aprobada','Desaprobada')),
    CONSTRAINT UQ_Matricula UNIQUE (EstudianteID, CursoID, Ciclo)
)
GO

FROM Matricula m

WHERE m.Nota IS NOT NULL
GROUP BY cu.Nombre

Caso para practicar: Tienda

Una tienda registra clientes (código autogenerado, nombres, DNI de 8 caracteres único y obligatorio, teléfono opcional) y productos (código autogenerado, descripción, precio mayor a cero, stock no negativo con valor por defecto 0). Cada pedido tiene número autogenerado, fecha (por defecto la fecha actual) y pertenece a un cliente. Un pedido incluye varios productos; de cada producto en el pedido se guarda la cantidad (mayor a cero) y el precio de venta.

Se pide: (a) script DDL completo con restricciones nombradas; (b) insertar 2 clientes, 3 productos y un pedido con 2 productos; (c) bajar 10% el precio de los productos con stock mayor a 50; (d) eliminar los clientes que no tienen pedidos; (e) listar el total vendido por pedido.

CREATE DATABASE TiendaDB
GO
USE TiendaDB
GO

CREATE TABLE Cliente (
    ClienteID INT IDENTITY(1,1) NOT NULL,
    Nombres   VARCHAR(120) NOT NULL,
    DNI       CHAR(8)      NOT NULL,
    Telefono  VARCHAR(15)  NULL,
    CONSTRAINT PK_Cliente PRIMARY KEY (ClienteID),
    CONSTRAINT UQ_Cliente_DNI UNIQUE (DNI)
)

CREATE TABLE Producto (
    ProductoID  INT IDENTITY(1,1) NOT NULL,
    Descripcion VARCHAR(150)  NOT NULL,
    Precio      DECIMAL(10,2) NOT NULL,
    Stock       INT           NOT NULL CONSTRAINT DF_Producto_Stock DEFAULT 0,
    CONSTRAINT PK_Producto PRIMARY KEY (ProductoID),
    CONSTRAINT CK_Producto_Precio CHECK (Precio > 0),
    CONSTRAINT CK_Producto_Stock  CHECK (Stock >= 0)
)

CREATE TABLE Pedido (
    PedidoID  INT IDENTITY(1,1) NOT NULL,
    Fecha     DATE NOT NULL CONSTRAINT DF_Pedido_Fecha DEFAULT GETDATE(),
    ClienteID INT  NOT NULL,
    CONSTRAINT PK_Pedido PRIMARY KEY (PedidoID),
    CONSTRAINT FK_Pedido_Cliente FOREIGN KEY (ClienteID) REFERENCES Cliente(ClienteID)
)

CREATE TABLE DetallePedido (
    PedidoID    INT           NOT NULL,
    ProductoID  INT           NOT NULL,
    Cantidad    INT           NOT NULL,
    PrecioVenta DECIMAL(10,2) NOT NULL,
    CONSTRAINT PK_DetallePedido PRIMARY KEY (PedidoID, ProductoID),
    CONSTRAINT FK_Detalle_Pedido   FOREIGN KEY (PedidoID)   REFERENCES Pedido(PedidoID),
    CONSTRAINT FK_Detalle_Producto FOREIGN KEY (ProductoID) REFERENCES Producto(ProductoID),
    CONSTRAINT CK_Detalle_Cantidad CHECK (Cantidad > 0)
)
GO

UPDATE Producto SET Precio = Precio * 0.90 WHERE Stock > 50

-- (d)
DELETE FROM Cliente
WHERE ClienteID NOT IN (SELECT ClienteID FROM Pedido)

-- (e)
SELECT PedidoID, SUM(Cantidad * PrecioVenta) AS Total
FROM DetallePedido
GROUP BY PedidoID

Antes de entregar

Checklist del examen

Caso 1 · Modelo físico

  • CREATE DATABASE + GO + USE al inicio.
  • Una tabla por entidad; las N:M tienen tabla intermedia.
  • Todas las tablas tienen PRIMARY KEY.
  • FK en el lado "muchos", con el mismo tipo de dato que la PK referenciada.
  • Tipos correctos: dinero en DECIMAL, DNI/teléfono en CHAR/VARCHAR, fechas en DATE.
  • UNIQUE, CHECK, DEFAULT y NOT NULL que pide el enunciado.
  • Restricciones nombradas (PK_, FK_, UQ_, CK_, DF_).
  • Tablas padre creadas antes que las hijas.
  • Comas entre columnas y ninguna coma antes del paréntesis final.

Caso 2 · DML

  • INSERT con lista de columnas explícita.
  • Insertar primero en tablas padre, luego en hijas.
  • No enviar columnas IDENTITY.
  • Textos y fechas entre comillas simples; números sin comillas.
  • Todo UPDATE y DELETE con WHERE (salvo que pidan afectar todo).
  • Para borrar un padre, borrar antes sus filas hijas.
  • IS NULL, nunca = NULL.
  • Columnas no agregadas del SELECT presentes en el GROUP BY.
  • WHERE filtra filas; HAVING filtra grupos.
