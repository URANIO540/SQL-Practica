Caso 1 · Modelo físico

DDL — Data Definition Language

DDL define y administra la estructura de la base de datos: crea, modifica y elimina objetos (bases de datos, tablas, restricciones). No trabaja con los datos, sino con la arquitectura que los sostiene. Con DDL el diseño lógico (entidades, atributos, relaciones) se convierte en una estructura física ejecutable.

CREATE: el punto de partida

Crea objetos nuevos. En el examen normalmente: primero la base de datos, luego USE para trabajar dentro de ella, y después las tablas.

CREATE DATABASE UniversityDB
GO
USE UniversityDB
GO

CREATE TABLE Student (
    StudentID  INT          PRIMARY KEY,
    FirstName  VARCHAR(100) NOT NULL,
    LastName   VARCHAR(100) NOT NULL,
    BirthDate  DATE,
    Email      VARCHAR(150) UNIQUE
)
¿Qué es GO?GO no es SQL: es un separador de lotes de SQL Server Management Studio. Úsalo después de CREATE DATABASE y antes de USE para que la base exista antes de entrar en ella.

Clave autoincremental: IDENTITY

Si el caso dice que el código se genera automáticamente, usa IDENTITY(inicio, incremento). En ese caso no envías ese valor en el INSERT.

CREATE TABLE Employee (
    EmployeeID INT IDENTITY(1,1) PRIMARY KEY,
    FirstName  VARCHAR(100) NOT NULL,
    Salary     DECIMAL(10,2) NOT NULL
)

-- No se envía EmployeeID: lo genera el motor
INSERT INTO Employee (FirstName, Salary) VALUES ('Luis Gomez', 2800.00)

Clave primaria compuesta

Cuando una fila se identifica por la combinación de dos columnas (típico en tablas intermedias N:M):

CREATE TABLE Detalle_Pedidos (
    id_pedido INT NOT NULL,
    id_producto INT NOT NULL,
    cantidad INT NOT NULL CHECK (cantidad > 0),
    PRIMARY KEY (id_pedido, id_producto),
    FOREIGN KEY (id_pedido) REFERENCES Pedidos(id_pedido),
    FOREIGN KEY (id_producto) REFERENCES Productos(id_producto)
)
GO
Orden de creaciónCrea primero las tablas independientes (las que no tienen FK) y después las que dependen de ellas. Si creas Enrollment antes que Student, la FK falla porque la tabla referenciada aún no existe.

ALTER: modificar sin eliminar

Permite adaptar el esquema a nuevos requerimientos sin perder la tabla ni sus datos.

-- Agregar una columna
ALTER TABLE Student
ADD Phone VARCHAR(20)

-- Cambiar el tipo de dato (sintaxis de SQL Server)
ALTER TABLE Student
ALTER COLUMN Phone VARCHAR(30)

-- Eliminar una columna
ALTER TABLE Student
DROP COLUMN Phone

-- Agregar una restricción a una tabla existente
ALTER TABLE Student
ADD CONSTRAINT CK_Student_BirthDate CHECK (BirthDate < '2015-01-01')

-- Agregar una FK después de crear las tablas
ALTER TABLE Enrollment
ADD CONSTRAINT FK_Enrollment_Course FOREIGN KEY (CourseID) REFERENCES Course(CourseID)

-- Eliminar una restricción (por eso conviene nombrarlas)
ALTER TABLE Student
DROP CONSTRAINT CK_Student_BirthDate
Ojo con otros motoresEn MySQL se usa MODIFY COLUMN y en PostgreSQL ALTER COLUMN ... TYPE. En el curso se usa SQL Server: ALTER COLUMN.

DROP, TRUNCATE y RENAME

DROP

Elimina el objeto completo: estructura y datos. Úsalo con precaución.

DROP TABLE Student

TRUNCATE

Borra todas las filas, pero la tabla (su definición) sigue existiendo.

TRUNCATE TABLE Student

sp_rename

En SQL Server se renombra con un procedimiento almacenado. Cambia el nombre, no la definición.

EXEC sp_rename 'Student', 'Learner'
-- columna:
EXEC sp_rename 'Student.Phone', 'Celular', 'COLUMN'

DDL y el diccionario de datos

Cada sentencia DDL actualiza el diccionario de datos: los metadatos que describen tablas, columnas, tipos, restricciones, índices y relaciones. El motor los usa para validar todas las operaciones posteriores. En SQL Server se consultan con vistas del sistema:

SELECT * FROM sys.tables          -- tablas existentes
SELECT * FROM sys.columns         -- columnas
SELECT * FROM sys.foreign_keys    -- claves foráneas
EXEC sp_help 'Student'            -- resumen completo de una tabla

-- Alternativa estándar
SELECT TABLE_NAME, COLUMN_NAME, DATA_TYPE, IS_NULLABLE
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 'Student'
DDL en entornos modernosEn ingeniería de datos, el DDL se trata como infraestructura como código: los scripts se versionan y herramientas como dbt generan CREATE/ALTER automáticamente, lo que permite automatizar despliegues y mantener consistencia entre ambientes.
Caso 2 · Manipulación de datos

DML — Data Manipulation Language

Mientras DDL define la estructura, DML trabaja con los datos almacenados en las tablas: insertar, modificar, eliminar y consultar registros. SELECT a veces se clasifica como DQL, pero funcionalmente forma parte de la manipulación de datos.

INSERT: agregar filas

Cada INSERT crea una fila nueva que debe cumplir todas las restricciones de la tabla.

-- Una fila (siempre lista las columnas: es más seguro)
INSERT INTO Employee (EmployeeID, FirstName, Salary)
VALUES (1, 'Luis Gomez', 2800.00)

-- Varias filas en una sola sentencia
INSERT INTO Employee (EmployeeID, FirstName, Salary)
VALUES
(2, 'Ana Torres', 3200.00),
(3, 'Carlos Ruiz', 2500.00)

-- Insertar a partir de una consulta
INSERT INTO EmployeeBackup (EmployeeID, FirstName, Salary)
SELECT EmployeeID, FirstName, Salary FROM Employee WHERE Salary > 3000
Al insertar, verifica • Columnas NOT NULL con valor.
• La PK no se repite.
• El valor de cada FK ya existe en la tabla padre → inserta primero en las tablas padre y luego en las hijas.
• Los CHECK se cumplen (ej. nota entre 0 y 20).
• Textos y fechas van entre comillas simples: '2026-10-11'. Números sin comillas.
• Si la PK es IDENTITY, no la envíes.

UPDATE: modificar filas existentes

Operación crítica: sin un WHERE correcto afecta a todas las filas.

-- Aumentar 10% el salario solo del área de ventas
UPDATE Employee
SET Salary = Salary * 1.10
WHERE Department = 'Sales'

-- Varias columnas a la vez
UPDATE Employee
SET Department = 'IT', Salary = 3500.00
WHERE EmployeeID = 2

-- Asignar NULL
UPDATE Student SET Email = NULL WHERE StudentID = 5

-- Valor condicional con CASE
UPDATE Matriculas
SET estado = CASE WHEN nota >= 13 THEN 'Aprobada' ELSE 'Desaprobada' END
WHERE nota IS NOT NULL
Sin WHEREUPDATE Employee SET Salary = Salary * 1.10 modifica todos los registros de la tabla. Truco: escribe primero el SELECT * FROM ... WHERE ..., comprueba qué filas devuelve y recién cambia a UPDATE.

DELETE: eliminar filas

DELETE FROM Employee
WHERE EmployeeID = 1

-- Sin WHERE: borra todas las filas, la tabla sigue existiendo
DELETE FROM Employee

Las claves foráneas pueden impedir la eliminación si existen filas hijas que dependen de la fila que intentas borrar. Opciones:

-- Opción 1: borrar primero las hijas y luego el padre
DELETE FROM Enrollment WHERE StudentID = 10
DELETE FROM Student    WHERE StudentID = 10

-- Opción 2: definir la FK con borrado en cascada (en el DDL)
CONSTRAINT FK_Enrollment_Student FOREIGN KEY (StudentID)
    REFERENCES Student(StudentID) ON DELETE CASCADE
Error típico en SQL Server"The DELETE statement conflicted with the REFERENCE constraint FK_..." significa que hay filas hijas. Por eso conviene nombrar las FK: el mensaje te dice exactamente cuál es.

DML y control transaccional

Los cambios hechos con DML no son permanentes hasta ejecutar COMMIT. Antes de eso, solo el usuario que hace los cambios los ve, se pueden revertir con ROLLBACK, y los demás usuarios siguen viendo el estado consistente anterior. Esto garantiza atomicidad (todo o nada) y consistencia.

BEGIN TRANSACTION

    UPDATE Cuentas SET saldo = saldo - 500 WHERE id_cuenta = 1
    UPDATE Cuentas SET saldo = saldo + 500 WHERE id_cuenta = 2

    -- Si todo salió bien:
COMMIT
    -- Si algo falló: ROLLBACK  (deshace ambos UPDATE)

-- Versión con control de errores
BEGIN TRY
    BEGIN TRANSACTION
        DELETE FROM Matriculas  WHERE id_estudiante = 10
        DELETE FROM Estudiantes WHERE id_estudiante = 10
    COMMIT
END TRY
BEGIN CATCH
    ROLLBACK
    PRINT ERROR_MESSAGE()
END CATCH
Dato de SQL ServerPor defecto SQL Server trabaja en modo autocommit: cada sentencia suelta se confirma sola. Solo dentro de BEGIN TRANSACTION puedes hacer ROLLBACK.
Consultas

La sentencia SELECT

Recupera información de una o más tablas. Permite filtrar filas, proyectar columnas, agrupar, aplicar funciones de agregación y ordenar.

Orden de escritura

SELECT→FROM→WHERE→GROUP BY→HAVING→ORDER BY

Columnas a mostrar · tablas origen · filtra filas · agrupa · filtra grupos · ordena.

Orden lógico de procesamiento

FROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BY

El motor procesa en este orden. Por eso un alias del SELECT no se puede usar en WHERE, pero sí en ORDER BY.

SELECT name, COUNT(OrderID) AS TotalPedidos
FROM Orders
WHERE status = 'Completed'          -- filtra FILAS (antes de agrupar)
GROUP BY name
HAVING COUNT(OrderID) > 5           -- filtra GRUPOS (después de agrupar)
ORDER BY TotalPedidos DESC          -- aquí ya se puede usar el alias

"Un mismo servicio puede ofrecerse en varios embarcaderos. Cada servicio asignado a un embarcadero cuenta con su propia tarifa base." La tarifa depende de la pareja (embarcadero, servicio):

CREATE TABLE Embarcaderos_Servicios (
    id_embarcadero INT NOT NULL,
    id_servicio INT NOT NULL,
    tarifa_base DECIMAL(10,2) NOT NULL CHECK (tarifa_base > 0),
    PRIMARY KEY (id_embarcadero, id_servicio),

)
GO

La cabecera guarda los datos generales y el detalle una fila por cada servicio. Como el detalle debe indicar dónde se adquirió el servicio, apunta a la tabla N:M con una FK de dos columnas:

    id_solicitud INT PRIMARY KEY,
    fecha_emision DATE NOT NULL,
    id_visitante INT NOT NULL,
    monto_total DECIMAL(10,2) NOT NULL DEFAULT 0,
    FOREIGN KEY (id_visitante) REFERENCES Visitantes(id_visitante)
)
GO

CREATE TABLE Detalle_Solicitudes (
    id_solicitud INT NOT NULL,
    id_embarcadero INT NOT NULL,
    id_servicio INT NOT NULL,
    cantidad INT NOT NULL CHECK (cantidad > 0),
    subtotal DECIMAL(10,2) NOT NULL,
    PRIMARY KEY (id_solicitud, id_embarcadero, id_servicio),
    FOREIGN KEY (id_solicitud) REFERENCES Solicitudes(id_solicitud),
    FOREIGN KEY (id_embarcadero, id_servicio)

Nomenclatura estándar (C04 / C08)

  • Tablas en plural, con guion bajo si son compuestas: Reservas_Marinas, Detalle_Solicitudes.
  • Tablas N:M con el nombre de las dos tablas: Embarcaderos_Servicios, Programas_Fases.
  • Columnas en minúscula con guion bajo: fecha_visita, monto_pagado.
  • PK con prefijo id_ en singular: id_reserva, id_embarcadero.
  • La FK se llama igual que la PK a la que apunta: Embarcaderos.id_reserva → Reservas_Marinas.id_reserva.
  • Sin tildes, espacios ni ñ en los nombres de tablas y columnas.

Examen: Vivienda y Urbanismo (PRONAVU)

Enunciado

El Programa Nacional de Vivienda y Urbanismo (PRONAVU) administra un sistema digital para la gestión, evaluación y financiamiento de planes habitacionales en todo el territorio nacional.

Con el objetivo de optimizar la asignación de recursos públicos y garantizar procesos transparentes, PRONAVU ha desarrollado una plataforma tecnológica que permite registrar postulantes, publicar programas de financiamiento, realizar evaluaciones técnicas y económicas, y asignar subsidios a los planes habitacionales aprobados.

Los postulantes deben estar registrados en el sistema y pueden ser personas naturales o jurídicas. En el caso de las personas naturales, se registra el nombre completo, DNI, dirección, teléfono y correo electrónico. Para las personas jurídicas, se almacena la razón social, dirección, RUC, nombre del representante legal, teléfono y correo electrónico. Cada postulante puede estar asociado a una o varias categorías del programa de financiamiento. Cada categoría del programa registra un código, descripción y una lista de programas de financiamiento. Entre los posibles valores de descripción de la categoría se incluyen: vivienda rural, conjuntos habitacionales, habilitación de servicios básicos e infraestructura comunitaria.

PRONAVU publica regularmente programas de financiamiento para otorgar subsidios a planes habitacionales. De cada programa de financiamiento se registra un código único, fecha de publicación, tipo de programa (subsidio directo, fondo concursable o programa especial), categoría del programa, descripción y monto asignado.

Cada programa de financiamiento se desarrolla en varias fases sucesivas, como publicación, postulación, evaluación técnica, evaluación económica y publicación de resultados. Una fase puede estar asociada a uno o varios programas de financiamiento. De cada fase se debe registrar un código único, descripción y tipo de fase (administrativa, técnica o económica). Cuando una fase se asigna a un programa de financiamiento, se debe registrar la fecha de inicio y la fecha de término.

Un postulante puede elaborar uno o varios planes habitacionales, aunque solo puede presentar un plan habitacional por programa de financiamiento. De cada plan habitacional se registra un código único, descripción, fecha de postulación, presupuesto solicitado, programa de financiamiento y postulante. Asimismo, cada programa de financiamiento puede recibir múltiples planes habitacionales.

Los planes habitacionales aprobados reciben financiamiento estatal. En estos casos, se registra la fecha de aprobación, el estado de ejecución (en ejecución, suspendida, cancelada) y monto desembolsado.

Examen: Aeropuertos Regionales (DIGAR)

Enunciado

La Dirección General de Aeropuertos Regionales (DIGAR) requiere sus servicios profesionales para administrar la información relacionada con los diferentes aeropuertos del país bajo su gestión.

De cada aeropuerto se debe registrar un código único, su nombre, ciudad en la que se encuentra, país y cantidad de pasajeros al año. Cada aeropuerto cuenta con una o varias terminales, y cada terminal pertenece únicamente a un aeropuerto. De las terminales se debe registrar un código, nombre, tipo de terminal (nacional, internacional o mixta).

Los pasajeros que transitan por los aeropuertos deben adquirir un boleto de embarque, el cual se puede obtener a través del portal web institucional o directamente en las ventanillas del aeropuerto correspondiente. De cada pasajero se requiere conocer su código único, el número de documento de identidad o pasaporte, el nombre completo, la fecha de nacimiento, ciudad y país de residencia. Cada pasajero puede adquirir varios boletos de embarque.

El boleto de embarque debe registrar un código único, pasajero, aeropuerto donde fue emitido, fecha de pago, fecha del vuelo, método de pago (tarjeta, efectivo, transferencia, etc.), tipo de boleto (nacional, internacional, ejecutivo, VIP, etc.), origen, destino y el monto pagado.

Además de los ingresos generados por los boletos de embarque, cada aeropuerto obtiene recursos adicionales a través de la prestación de servicios. De esta manera, cada terminal gestiona un catálogo de servicios que puede incluir el acceso a salas VIP, la conexión Wi-Fi premium, la asistencia personalizada de equipaje o el uso de estacionamientos preferenciales.

Un mismo servicio puede ofrecerse en una o varias terminales. De cada servicio se debe registrar su código, descripción y el tipo de servicio (confort, conectividad, asistencia o transporte). Asimismo, cada servicio asignado a una terminal específica debe contar con su propia tarifa base.

Los pasajeros pueden generar una o varias solicitudes que incluye los servicios durante su estadía en la terminal. Una solicitud debe registrar código, fecha, pasajero, monto total y una lista de servicios adquiridos. De cada servicio solicitado se debe incluir la terminal, cantidad y monto subtotal.

Ver decisiones de diseño
  • Es el mismo esqueleto que DIGREMAR, cambiando reserva → aeropuerto, embarcadero → terminal, visitante → pasajero y ticket → boleto. Si dominas uno, dominas el otro.
  • Catálogos: método de pago y tipo de boleto terminan en "etc.", así que van en tablas Metodos_Pago y Tipos_Boleto. El tipo de terminal (nacional, internacional o mixta) y el tipo de servicio son listas cerradas: van con CHECK.
  • Origen y destino: se guardan como texto (ciudad o código IATA), porque pueden ser aeropuertos que DIGAR no administra (por ejemplo, París). Si el caso dijera que siempre son aeropuertos registrados, serían dos FK a Aeropuertos.
  • N:M con tarifa: Terminales_Servicios (id_terminal, id_servicio, tarifa_base).
  • Detalle con FK compuesta hacia Terminales_Servicios, para que solo se puedan pedir servicios que esa terminal ofrece.
  • Cantidad de pasajeros al año: es un dato del aeropuerto (INT), no se calcula.

Examen: Formación Empresarial (REPEM)

Enunciado

La Red Peruana de Formación Empresarial (REPEM) administra un sistema digital para la gestión, evaluación y seguimiento de programas de capacitación y mentoría empresarial dirigidos a micro, pequeñas y medianas empresas (MYPES).

Con el propósito de fortalecer la competitividad y sostenibilidad del ecosistema empresarial, REPEM ha desarrollado una plataforma tecnológica que permite registrar postulantes, publicar programas de apoyo con incentivo económico, y asignar asesorías o financiamiento a los planes de negocio seleccionados.

Los postulantes deben estar registrados en el sistema y pueden ser personas naturales o jurídicas. En el caso de las personas naturales, se registra el nombre completo, el DNI, la dirección, el teléfono y el correo electrónico. Para las personas jurídicas, se almacena la razón social, la dirección, el RUC, el nombre del representante legal, el teléfono y el correo electrónico. Cada postulante puede estar vinculado a una o varias categorías empresariales, las cuales registran un código, una descripción y una lista de programas de capacitación. Entre los posibles valores de descripción de la categoría empresarial se incluyen: comercio minorista, servicios tecnológicos, industria manufacturera, emprendimientos verdes y servicios creativos.

REPEM publica periódicamente programas de capacitación con el fin de brindar acompañamiento técnico y apoyo financiero a los emprendimientos seleccionados. De cada programa de capacitación se registra un código único, la fecha de publicación, el tipo de programa (capacitación técnica, mentoría empresarial o fondo concursable), la categoría empresarial a la que se dirige, una descripción, el monto de financiamiento y el presupuesto total del programa.

Cada programa de capacitación se desarrolla en varios módulos sucesivos, tales como ideación y validación, modelo de negocio, finanzas para emprendedores, marketing y ventas y mentorías personalizadas. Un mismo módulo puede estar asociado a varios programas. De cada módulo se registra un código, una descripción y el tipo de módulo (técnico, estratégico o transversal). Cuando un módulo se asigna a un programa, se registran su fecha de inicio, fecha de fin, la modalidad (presencial/virtual/híbrida) y el número de participantes.

Un postulante puede elaborar uno o varios planes de negocio, pero solo puede presentar uno por programa de capacitación. De cada plan de negocio se registra un código único, una descripción general, la fecha de postulación, el presupuesto solicitado, el programa de capacitación y el postulante. Asimismo, cada programa puede recibir múltiples planes de negocio.

Por último, los planes de negocio aprobados reciben asesoría o financiamiento. En estos casos, se registra la fecha de inicio, la duración y el monto asignado.

Ver decisiones de diseño
  • Mismo esqueleto que PRONAVU: programa de financiamiento → programa de capacitación, fase → módulo, plan habitacional → plan de negocio, financiamiento → apoyo.
  • Subtipos: Postulantes (datos comunes) + Personas_Naturales + Personas_Juridicas, con PK = FK.
  • N:M con varios atributos: la fecha de inicio y fin, la modalidad y el número de participantes son de la asignación módulo–programa: van en Programas_Modulos. La modalidad es una lista cerrada (presencial/virtual/híbrida), así que lleva CHECK.

  • Asesoría o financiamiento: un plan aprobado tiene como máximo un apoyo → tabla Apoyos con id_plan como PK y FK. Supuesto: se agrega tipo_apoyo para distinguir asesoría de financiamiento. La duración se guarda en meses (INT).
  • Monto vs. presupuesto: el programa tiene dos montos distintos (financiamiento por plan y presupuesto total). Son dos columnas DECIMAL.

    id_programa INT PRIMARY KEY,
    fecha_publicacion DATE NOT NULL,
    tipo_programa VARCHAR(25) NOT NULL

    id_categoria INT NOT NULL,
    descripcion VARCHAR(200) NOT NULL,
    monto_financiamiento DECIMAL(12,2) NOT NULL CHECK (monto_financiamiento >= 0),

    FOREIGN KEY (id_categoria) REFERENCES Categorias_Empresariales(id_categoria)

    id_modulo INT PRIMARY KEY,

CREATE TABLE Programas_Modulos (
    id_programa INT NOT NULL,
    id_modulo INT NOT NULL,

    num_participantes INT NOT NULL CHECK (num_participantes >= 0),

    FOREIGN KEY (id_programa) REFERENCES Programas_Capacitacion(id_programa),

    id_postulante INT NOT NULL,

    FOREIGN KEY (id_postulante) REFERENCES Postulantes(id_postulante),

)
GO

CREATE TABLE Apoyos (

Checklist del examen

Caso 1 · Modelo físico

  • CREATE DATABASE + GO + USE al inicio.
  • Una tabla por entidad; las N:M tienen tabla intermedia.
  • Todas las tablas tienen PRIMARY KEY.
  • FK en el lado "muchos", con el mismo tipo de dato que la PK referenciada.
  • Tipos correctos: dinero en DECIMAL, DNI/teléfono en CHAR/VARCHAR, fechas en DATE.
  • UNIQUE, CHECK, DEFAULT y NOT NULL que pide el enunciado.
  • Nombres al estilo de la profesora: tablas en plural, columnas tipo id_cliente.
  • Tablas padre creadas antes que las hijas.
  • Comas entre columnas y ninguna coma antes del paréntesis final.

Caso 2 · DML

  • INSERT con lista de columnas explícita.
  • Insertar primero en tablas padre, luego en hijas.
  • No enviar columnas IDENTITY.
  • Textos y fechas entre comillas simples; números sin comillas.
  • Todo UPDATE y DELETE con WHERE (salvo que pidan afectar todo).
  • Para borrar un padre, borrar antes sus filas hijas.
  • IS NULL, nunca = NULL.
  • Columnas no agregadas del SELECT presentes en el GROUP BY.
  • WHERE filtra filas; HAVING filtra grupos.
